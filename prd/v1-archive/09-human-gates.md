# 09 - 人工 Gate 详细规范

## 一、Gate 设计总览

```
┌──────────────────────────────────────────────────────────┐
│  Gate 1 (Stage 1 后)   - PM/BA                          │
│  ├─ 评审：需求理解 + 验收标准                            │
│  ├─ SLA：4h 放行/驳回                                    │
│  └─ 角色：PM、BA、需求提出方                             │
│                                                          │
│  Gate 2 (Stage 2 后)   - 架构师/Tech Lead               │
│  ├─ 评审：架构决策 + 技术方案                            │
│  ├─ SLA：8h 放行/驳回                                    │
│  └─ 角色：架构师、TL                                     │
│                                                          │
│  Gate 3 (Stage 4 后)   - Tech Lead（条件触发）           │
│  ├─ 触发：Stage 4 标 P0/P1 时                            │
│  ├─ 评审：风险修复 + 关键代码                            │
│  ├─ SLA：4h                                             │
│  └─ 角色：TL、CR 经验者                                  │
│                                                          │
│  Gate 4 (Stage 7 后)   - SRE/QA                         │
│  ├─ 评审：监控 + Runbook + 上线准备                      │
│  ├─ SLA：4h                                             │
│  └─ 角色：SRE、QA                                       │
└──────────────────────────────────────────────────────────┘
```

## 二、Gate 1：需求评审

### 2.1 评审输入

- `prd/{feature_id}/01-requirements.md`
- 原始 PRD
- 评审 Checklist（见 §2.3）

### 2.2 评审工具

主对话自动用 `AskQuestion` 提供 4 选 1：

```
[Gate 1] 评审 {feature_id} - {feature_name}

Q1. 需求拆解质量如何？
- ✅ 通过（业务目标清晰、验收标准可量化、异常覆盖完整）
- ⚠️ 通过（有小瑕疵，Subagent 同步修复后继续）
- ❌ 驳回（关键问题，需 Stage 1 重做）
- 🅿️ 暂停（信息不全，需补 PRD/澄清）
```

### 2.3 评审 Checklist

#### A. 业务目标（必查）

- [ ] 准确反映 PRD 业务意图（不超过 3 句话）
- [ ] 与 PRD 中"为什么要做"一致
- [ ] 无 AI 主观臆测

#### B. 用户故事（必查）

- [ ] 角色完整（至少包含直接用户 + 间接用户）
- [ ] 每条 US 含"动作-价值"
- [ ] 无遗漏关键场景

#### C. 功能清单（必查）

- [ ] 主流程 ≥ 3 条
- [ ] 异常流程 ≥ 5 条
- [ ] 无漏掉的"小功能"（如日志、埋点）

#### D. 验收标准（必查）

- [ ] 每条功能 ≥ 1 条 Given-When-Then
- [ ] Then 必须可量化（数字/状态/字符串）
- [ ] 禁止"正常""正确"等模糊词

#### E. 影响面（必查）

- [ ] 上下游系统识别完整
- [ ] 风险等级合理（无漏标 P0）

#### F. 开放问题（必查）

- [ ] ≥ 0 条（PRD 模糊点必须列）
- [ ] 已在 PM 决策范围

### 2.4 驳回处理

```
驳回 → Stage 1 重做
     ↓
Subagent 收到驳回原因
     ↓
重新生成
     ↓
再次提交 Gate 1
     ↓
最多 3 轮，超过升级到 D 类
```

### 2.5 放行产物

- 更新 `meta.json`：
  ```json
  {
    "gate1_status": "approved",
    "gate1_reviewer": "PM 张三",
    "gate1_timestamp": "2026-06-05T10:00:00Z",
    "gate1_comments": "...",
    "gate1_round": 1
  }
  ```
- 触发 Stage 2

## 三、Gate 2：架构评审

### 3.1 评审输入

- `prd/{feature_id}/02-design/` 全套
- 上一 Gate 的需求文档
- 评审 Checklist

### 3.2 评审 Checklist

#### A. 架构合理性（必查）

- [ ] 整体架构 KISS（不过度设计）
- [ ] 模块划分合理（高内聚低耦合）
- [ ] 与现有架构一致

#### B. DongBoot 组件选型（必查）

- [ ] 缓存场景使用 DongCache
- [ ] HTTP 调用使用 DongHttp
- [ ] 锁场景使用 DongLock
- [ ] ID 生成使用 DongSequence
- [ ] 调度使用 DongSchedule
- [ ] 线程池使用 DongThread
- [ ] DB 访问使用 DongDAL
- [ ] MQ 使用 internal-mq
- [ ] 业务日志使用 DongLog
- [ ] 每个选型都有 ADR 支撑

#### C. ADR 质量（必查）

- [ ] 每个关键决策有 ADR
- [ ] 备选方案 ≥ 2 个
- [ ] 后果分析完整

#### D. API 契约（必查）

- [ ] 接口命名一致
- [ ] 入参/出参明确
- [ ] 错误码定义
- [ ] 超时配置（internal-rpc/HTTP）
- [ ] 限流配置

#### E. 库表设计（必查）

- [ ] 字段类型合理
- [ ] 索引覆盖查询
- [ ] 无大字段（text/blob）滥用
- [ ] 软删/硬删策略

#### F. 影响面（必查）

- [ ] 上下游接口影响已识别
- [ ] DB 变更已列出
- [ ] 配置变更已列出
- [ ] 数据迁移已说明

#### G. 风险（必查）

- [ ] 性能风险已识别并缓解
- [ ] 安全风险已识别并缓解
- [ ] 数据一致性风险已说明

#### H. 工作量（参考）

- [ ] 与团队规模匹配
- [ ] 有明确的并行/串行计划

### 3.3 驳回处理

```
驳回 → Stage 2 重做
     ↓
Subagent 收到驳回原因
     ↓
重新生成
     ↓
再次 Gate 2
     ↓
最多 3 轮
```

### 3.4 强制升级

如果 Gate 2 驳回原因为以下之一，**强制升级到架构组会议**：
- 涉及跨系统架构调整
- 引入新的中间件/组件
- 影响核心数据模型

## 四、Gate 3：CR 风险评审

### 4.1 触发条件

```
Stage 4 输出 04-review.md
   ↓
存在 P0 → 必触发
存在 P1 → 必触发
P2 ≥ 3 → 必触发
否则 → 不触发，Stage 4 自动通过
```

### 4.2 评审输入

- `prd/{feature_id}/04-review.md`
- Git diff
- 修复方案（如有）

### 4.3 评审 Checklist

#### A. P0 修复（必查）

- [ ] 修复方案合理
- [ ] 不引入新问题
- [ ] 有测试覆盖

#### B. P1 修复（必查）

- [ ] 性能影响已评估
- [ ] 有 benchmark 数据

#### C. P2 决策（必查）

- [ ] 是否可接受延后修复
- [ ] 是否有 follow-up 工单

#### D. 整体评价（必查）

- [ ] 代码可读性
- [ ] 维护成本
- [ ] 团队规范符合度

### 4.4 驳回处理

```
驳回 → 回到 Stage 3 重做（不是 Stage 4）
     ↓
coder-backend Subagent 收到修复要求
     ↓
重新生成
     ↓
再次 Stage 4（CR）
     ↓
再次 Gate 3
     ↓
最多 3 轮
```

## 五、Gate 4：上线准备评审

### 5.1 评审输入

- `prd/{feature_id}/07-monitor/` 全套
- 上线 Checklist
- 业务方已确认

### 5.2 评审 Checklist

#### A. 监控盘（必查）

- [ ] 核心业务指标覆盖
- [ ] 1 屏可见主要指标
- [ ] 每个指标可下钻
- [ ] 阈值合理（不抖动）

#### B. 告警规则（必查）

- [ ] P0 告警 ≤ 2 条（过多会疲劳）
- [ ] 通知对象正确
- [ ] 响应 SLA 合理
- [ ] 误报率预期 < 10%

#### C. Runbook（必查）

- [ ] 每个 P0/P1 告警对应章节
- [ ] 现象描述具体（"什么算下跌"）
- [ ] 定位步骤可执行（命令/UI 路径）
- [ ] 恢复动作明确
- [ ] 升级路径清晰

#### D. SLO（必查）

- [ ] 与 PRD 性能边界一致
- [ ] 错误预算计算合理
- [ ] 告警阈值与 SLO 联动

#### E. 上线 Checklist（必查）

- [ ] 所有项可勾选
- [ ] 业务方已确认
- [ ] 应急联系已就绪
- [ ] 时间窗口已确认

### 5.3 驳回处理

```
驳回 → Stage 7 重做
     ↓
sre-writer Subagent 收到驳回原因
     ↓
重新生成
     ↓
再次 Gate 4
     ↓
最多 3 轮
```

## 六、紧急 Gate（Hotfix）

### 6.1 触发场景

- 生产 P0 故障
- 安全漏洞
- 监管合规紧急需求

### 6.2 精简流程

```
PRD（口头/IM）
   ↓
Gate 1（30 min 放行/驳回）
   ↓
Stage 2（30 min）
   ↓
Gate 2（30 min）
   ↓
Stage 3 + 4（合并，1h）
   ↓
Gate 3（仅 P0/P1）
   ↓
Stage 5（关键路径，30 min）
   ↓
Stage 6（直发 prod 灰度，1h）
   ↓
Stage 7（监控补全，1h）
   ↓
Gate 4（30 min）
```

总耗时：4-5h。

### 6.3 后续补全

- Hotfix 上线后 24h 内，必须补全正常 Gate 流程
- 形成"Hotfix 复盘"文档
- 更新 Runbook

## 七、Gate 状态管理

### 7.1 状态机

```
pending → in_review → approved | rejected | paused
                ↓
            (多轮循环)
                ↓
              approved
```

### 7.2 SLA 监控

| Gate | 标准 SLA | 超时升级 |
|---|---|---|
| 1 | 4h | 通知 PM 主管 |
| 2 | 8h | 通知架构组 leader |
| 3 | 4h | 通知 TL 主管 |
| 4 | 4h | 通知 SRE 主管 |

超时未响应视为"暂停"，流水线挂起。

### 7.3 统计指标

- **Gate 通过率**：approved / total
- **平均放行时间**：放行时间 - 提交时间
- **驳回率**：rejected / total
- **多轮率**：超过 1 轮 / total
- **AI 误判率**：人工驳回 / AI 自评通过

## 九、人工 Gate 的"自检"

为防止人工 Gate 流于形式，**主对话在每次 Gate 提交时自动执行**：

1. 校验产物文件存在
2. 校验产物符合模板
3. 自动列出 Checklist 勾选项
4. 计算 AI 自信度（如有）
5. 推荐评审人（基于历史经验）

评审人可参考 Checklist 但**必须独立判断**。
