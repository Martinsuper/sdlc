# 阶段：归档（archive）

把一个**已完成/不再活跃**的需求的全部关联文档，整体搬到归档区，让 `.sdlc/` 主区只保留在办需求，保持清爽。执行后先列出可归档的需求供用户选择，再把所选需求的所有阶段文档搬到 `.sdlc/_archive/` 下。

这是操作型阶段（会移动文件），不产出结构化文档。

## 输入

- 无参数：扫描并列出所有可归档需求，让用户选。
- 带参数（需求名/slug）：直接定位该需求，跳过选择列表。

## 前置检查

- 确认项目根存在 `.sdlc/` 目录；不存在则告知"当前项目没有 SDLC 产物可归档"。
- 本阶段无需探测项目画像。

## 执行

**第一步：探测布局，列出可归档需求。**

`.sdlc/` 有两种布局，先判断是哪种：

```bash
# 看 .sdlc/ 直下有没有 slug 需求目录(非数字前缀阶段目录、非 _archive、非 00-context)
ls -d .sdlc/*/ 2>/dev/null
```

- **多需求布局**（存在 `.sdlc/<slug>/01-prd/...` 这种嵌套）：每个 slug 子目录是一个需求。列出所有 slug 作为候选。
- **单需求布局**（阶段目录 `01-prd/`…直接在 `.sdlc/` 下）：整个 `.sdlc/` 就是一个需求。候选只有它一个。

对每个候选需求，读其 `01-prd/00-requirements.md`（或最靠前的产物）顶部元信息块的**需求名**与**日期**、以及当前进展阶段，组织成带编号的列表给用户：

```
可归档的需求：
  1. 账单发票类目  （slug: billing-invoice ｜ 已到 06-deploy ｜ 2026-07-10）
  2. 优惠券叠加     （slug: coupon-stack   ｜ 已到 03-review ｜ 2026-07-18）
请选择要归档的需求编号（可多选，逗号分隔）：
```

- 单需求布局时，列表只有一项（该项 = 整个 `.sdlc/` 的阶段目录集合）。
- `00-context/`（上下文资料库）和已有的 `_archive/` **不作为归档候选**，跳过。

**第二步：确认归档清单。**

用户选定后，列出**将要搬动的具体内容**和**目标路径**，让用户看一眼（选择即确认，不再逐文件追问）：

```
将归档需求「账单发票类目」：
  .sdlc/billing-invoice/          →  .sdlc/_archive/账单发票类目-20260722/
    （含 01-prd 02-design 03-review 04-code 05-test 06-deploy 等全部阶段文档）
```

- 目标目录名 = `<需求名>-<归档日期 YYYYMMDD>`；需求名含特殊字符时用 slug 兜底。
- 目标已存在同名归档目录 → 停下来问用户（改名/覆盖/取消），不静默覆盖。

**第三步：执行搬动。**

在 git 仓库内优先用 `git mv` 保留历史，否则用 `mv`：

```bash
mkdir -p .sdlc/_archive
# 多需求：搬整个 slug 目录
git mv .sdlc/<slug> ".sdlc/_archive/<需求名>-<日期>"   2>/dev/null || mv .sdlc/<slug> ".sdlc/_archive/<需求名>-<日期>"
# 单需求：把各阶段目录归拢到一个归档目录下
mkdir -p ".sdlc/_archive/<需求名>-<日期>"
for d in 01-prd 02-design 03-review 04-code 05-test 06-deploy *-report; do
  [ -e ".sdlc/$d" ] && { git mv ".sdlc/$d" ".sdlc/_archive/<需求名>-<日期>/" 2>/dev/null || mv ".sdlc/$d" ".sdlc/_archive/<需求名>-<日期>/"; }
done
```

- 单需求布局下 **不搬 `00-context/`**（上下文资料是跨需求复用的，留在主区）。
- 搬完后 `.sdlc/` 主区应只剩在办需求与 `00-context/`、`_archive/`。

## 产出

- 主要是**动作**（把所选需求的文档搬到 `.sdlc/_archive/<需求名>-<日期>/`），不产出新文档。
- 终端输出归档结果摘要：归档了哪个需求、搬了多少个阶段目录、归档目标路径。

## 交接

展示：已归档的需求名 + 归档路径 + `.sdlc/` 主区剩余需求。归档是收尾动作，不自动进入其他阶段——等用户下一步指令（可能是开新需求 `clarify`，或 `status` 看剩余进度）。
