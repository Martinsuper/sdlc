# 阶段：需求澄清（clarify）

把一个模糊的需求变成结构化、可验收的功能规格，为后续设计打地基。这是全流程的**强制起点**：本阶段产出的需求文档（PRD）是进入 design 的前置门禁——没有它不允许直接设计（见 SKILL.md「流程门禁」）。设计和评审的质量上限由这里决定。

> **边界红线（本阶段最重要的约束）：只描述客观需求，不涉及任何方案设计。**
> clarify 只回答"要解决什么问题、做成什么样、怎样算做对了"，**绝不**回答"用什么技术、怎么实现、系统怎么分层/建表/设计接口"。
> - **允许**：业务目标、用户/场景、功能行为（从用户视角的输入→输出→异常）、业务规则、数据的业务含义、非功能诉求（性能/安全/合规的目标值）、验收标准、范围边界。
> - **禁止**：技术选型、架构/模块划分、数据库表与字段设计、接口/API 设计、类名/函数名、算法与实现步骤、框架/中间件、代码。
> - 若用户主动给了技术方案倾向，记录到"开放问题/约束"里备查，但**不在需求里展开设计**——那是 design 阶段的事。
> - 判据：一句话若回答的是"怎么做"而非"要什么"，它就不属于 clarify，删掉或挪到 design。

## 输入

- 用户的自然语言需求描述，或
- PRD 链接（使用当前客户端可用的文档读取工具读取），或
- 一段零散的想法。

## 前置检查

- 若给了 PRD 链接，先读全文再澄清，不要只凭标题猜。
- 需求已经很清晰时，仍要固化出需求文档 PRD（可精简，但不可为空）——它是 design 的强制前置。用户即便说"直接设计"，也要先落一份精简 PRD，除非用户显式声明"知道风险、强制跳过澄清"。
- 本阶段无需探测项目画像（还没进入技术细节）。

## 执行

分两轮，别一次抛太多问题淹没用户：

**第一轮：识别模糊点，生成澄清清单。** 通读需求，从这些角度找出"没说清楚 / 有多种理解 / 有隐含假设"的点：

- **范围边界**：做什么、明确不做什么；这次和下次的分界。
- **功能细节**：核心业务流程的每一步（用户视角的输入/输出/异常分支）；边界值。不追问技术实现。
- **数据**：涉及哪些业务实体（不是数据库表）、数据来源、量级、生命周期与业务含义。
- **非功能约束**：性能（QPS/延迟）、并发、一致性要求、安全/权限、合规——只问目标，不问手段。
- **兼容性**：对存量用户/数据/既有业务行为的影响（从业务结果看，不追问接口/表结构怎么改）。
- **依赖与协作**：依赖哪些上下游、谁提供、是否已对齐。
- **验收标准**：怎样算"做完了"、怎样算"做对了"。

把这些整理成一次 5–10 个高价值问题问用户，标出哪些是阻塞性的（不回答无法设计）。**对其中"选项能预先枚举"的问题（如范围二选一、是否需要某能力、目的属于哪类），用当前客户端的结构化提问工具渲染成可点选项，而不是列编号让用户敲字**（OpenCode 使用 `question`，Claude Code 使用 `AskUserQuestion`；约定见 SKILL.md「交互约定」总纲）；纯开放式问题（如"业务目标是什么"）无法枚举选项，仍用文字提问。

**第二轮：固化规格。** 用户回答后（可能多轮），把澄清结果整理成结构化功能规格：

- 需求背景与目标（一句话价值 + 要解决的问题）
- 功能列表（每条：描述 + 输入 + 输出 + 主要流程 + 异常处理）——**均从用户/业务视角描述行为**：输入输出指业务上的信息而非接口字段，"主要流程"指用户看到的业务步骤而非代码调用链，异常处理指业务上如何表现而非 try/catch。
- 非功能需求（性能/安全/兼容性/合规，逐条量化）——只写**目标值**（如"P99 < 200ms"），不写达成手段（如"加缓存"）。
- 明确的范围外事项（Out of Scope）
- 验收标准（可测量、可勾选）——以可观察的业务结果表述，不绑定实现。
- 尚未解决/待外部确认的开放问题（用户提到的技术倾向/约束也记这里，不展开设计）

## 产出

写入 `.sdlc/01-prd/00-<需求名>.md`——文件名的 `<需求名>` 取自下方元信息块的「需求名称」，压缩成无空格短名（中文保留、去掉空格/斜杠等特殊字符，建议 ≤ 20 字），**不要用 `requirements` 这类阶段通用词**（命名规约见 SKILL.md「产物目录规约」）。后续 design/review 等阶段沿用同一需求名。顶部元信息块：

```
> 需求名称：<name>
> 日期：<YYYY-MM-DD>
> 状态：已澄清 / 待确认（有开放问题）
> 关联：（暂无）
```

## 交接

先用文字展示产出路径 + 需求一句话摘要 + 开放问题数量。随后**调用当前客户端的结构化提问工具**给出可点选的下一步（约定见 SKILL.md「交互约定」，禁止只用文字罗列），选项对应：

- 进入 **design** 阶段（我会带着这份规格做方案设计）——默认首选项
- 先补充/修改澄清内容
- 有开放问题，需用户去外部对齐后再继续

若用户选择继续，进入 `references/design.md`，并把本产出作为 design 的主要输入。
