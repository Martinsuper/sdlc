# 阶段：编码实现（code）

把设计变成代码。这一步 Claude Code 本体最擅长——本阶段的职责是**编排 + 规范注入 + 自检**，而不是复述如何写代码。

## 输入

- 设计文档路径（`.sdlc/02-design/` 下的 `00-<需求名>.md`），或
- 用户直接指定的开发单元/改动点。
- 也可只给数字前缀（如 `01`）快捷选中设计文档 `.sdlc/02-design/01-*.md`，评审报告在 `.sdlc/03-review/` 取同一前缀 `01-*.md`（`1`/`01` 等价）；定位与歧义处理见 SKILL.md「产物目录规约·数字前缀选择」。

## 前置检查

1. **前置门禁——必须有评审通过的设计**：确认 `.sdlc/02-design/` 下存在设计文档、`.sdlc/03-review/` 下存在评审报告（均扫描目录定位 `00-<需求名>.md`），且评审报告结论为「通过」。无设计、无评审、或评审结论为「不通过 / 有条件通过」时**默认拦截**，要求先补齐 design → review 通过再开发。仅当用户显式声明"知道风险、强制跳过"时放行，并在实现说明里标注跳过留痕。
2. **探测项目画像**：读 `references/profiles.md`，了解技术栈——影响遵循的编码规范（命名、分层、错误处理惯例）。
3. **读现有代码规范与上下文**：若项目有 `CLAUDE.md`、`.editorconfig`、lint 配置、或明显的代码风格，遵循它们，不要引入与现有风格冲突的写法。若存在 `.sdlc/00-context/`，一并参考其中的架构文档/知识库/技术规范，确保实现对齐团队既有约定。

## 执行

**第一步：拆解开发单元。** 从设计文档拆出有序的开发单元（按依赖关系排序：数据结构/模型 → 数据访问 → 业务逻辑 → 接口层 → 前端对接）。单元之间有依赖时串行，独立时可并行。

**第二步：逐单元实现。** 每个单元：

- 遵循项目既有模式（找一个类似的现有文件参照），不要另起一套。
- 只做设计要求的改动——不顺手重构、不加设计外的抽象、不加用不到的错误处理（遵循仓库 CLAUDE.md 的工程约束）。
- 涉及外部边界（用户输入、外部 API）才做校验；内部调用信任类型与框架保证。

**第三步：自检。** 每个单元或一组相关单元完成后，建议调用现成能力自检，别自己重造：

- `code-review` skill —— 审当前 diff 的正确性与可简化点。
- `verify` skill / `run` skill —— 端到端跑一遍受影响的流程，确认真的能用（尤其 UI/接口改动，类型检查通过 ≠ 功能正确）。
- 项目已有的 lint / type-check / 测试命令。

## 产出

- **主产出是代码变更本身**（在源码树里）。
- 可选：`.sdlc/04-code/00-<需求名>.md` 记录实现说明——只在有"设计外的决策/权衡/坑"值得留痕时写，否则不写（避免为凑文档而写文档）。若写，包含：实现与设计的偏差及原因、遗留 TODO、需要评审注意的点。

## 交接

先用文字展示：改了哪些文件（概要）+ 自检结果（lint/测试/verify 是否通过）+ 与设计的偏差（若有）。随后**调用 `AskUserQuestion` 工具**给出可点选的下一步（约定见 SKILL.md「交互约定」，禁止只用文字罗列），选项对应：

- 进入 **test** 阶段补齐测试——默认首选项
- 继续实现下一批单元
- 做一次完整的 code-review

如果自检发现问题且无法当场解决，如实说明，不要谎报"已完成"。
