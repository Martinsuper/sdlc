# 阶段：上线计划（deploy）

产出一份可执行的上线计划：变更范围、配置修改、上线步骤（含回滚）、上线后检查清单。检查清单按项目画像裁剪，非 JVM/非企业内部栈不出现对应项。

## 输入

- 设计文档（`.sdlc/02-design/` 下的 `00-<需求名>.md`），和/或
- git 变更（分析 diff 确定变更范围），和/或
- 用户的变更说明。

## 前置检查

1. **前置门禁——必须有实现基础**：上线 checklist 是流程收尾产物，前提是已有编码产出（代码变更 / `.sdlc/04-code`），通常也应已过测试（`.sdlc/05-test`）。无任何实现就做上线计划属于空转——缺失时默认拦截并提示先完成开发/测试；用户显式声明强制跳过时放行并留痕。
2. **探测项目画像**：读 `references/profiles.md`，得出上线检查清单启用哪些标签（`[jvm-runtime]`/`[mq]`/`[cache]`/`[enterprise-infra]` 等）。
3. **分析变更范围**：
   ```bash
   git status
   git diff --stat
   git log --oneline -10
   ```
   识别涉及的服务/部署单元、配置文件改动、SQL 变更、依赖变更。

## 执行

**第一步：梳理配置与数据变更。**

- 静态配置改了什么、动态配置（配置中心）改了什么。
- SQL 调整：DDL/DML 清单，标注是否需 DBA/负责人验证。
- **强烈建议新功能加业务开关**——能快速关闭，是最有效的回滚手段。

**第二步：制定分步上线步骤。** 每一步都配对应的回滚步骤：

| 上线节奏 | 执行步骤 | 回滚步骤 |
| --- | --- | --- |

按"灰度 → 放量 → 全量"的节奏拆分，标注每步的观察点。

**第三步：生成上线后检查清单。** 用 `templates/release-plan.md`，按启用标签裁剪：

- **通用核心指标**（始终有）：健康探针/存活、核心业务量、QPS/调用量、错误率、P99 延迟、本次新增监控项。
- `[mq]` → 消息队列消费情况。
- `[cache]` → 缓存命中/可用性。
- `[jvm-runtime]` → JVM 内存/GC。
- 容器/资源：实例数、CPU/内存/磁盘。
- `[enterprise-infra]` → 内部监控体系专有项（默认不出现）。
- 收尾项：接口返回值是否变更、业务开关状态、监控一段时间（如 20 分钟）确认稳定再离开。

## 产出

写入 `.sdlc/06-deploy/00-<需求名>.md`（`<需求名>` 沿用设计的需求名，勿用 `release-plan` 通用词）。顶部元信息块：

```
> 上线主题：<title>
> 版本：<version>
> 日期：<YYYY-MM-DD>
> 状态：待评审 / 已通过 / 已上线
> 关联：.sdlc/02-design/00-<需求名>.md
```

## 交接

展示：上线主题 + 变更范围摘要 + 关键风险 + 是否已设计回滚。提醒用户：

- 所有 SQL 调整需相应负责人验证。
- 上线步骤必须每步可回滚。
- 确认上线人员、时间窗口。

这是流程的终点，收尾时可提示用户跑 `sdlc status` 查看整条链路的完整产出。
