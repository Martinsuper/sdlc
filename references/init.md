# 阶段：项目初始化（init）

全流程的**前置准备**阶段。在正式跑 clarify/design 等阶段之前，把项目环境和文档基础准备好：初始化代码检索索引、检查现有文档是否符合 SDLC 文档标准、把散落的研发文档归位到规范目录。

这是操作型阶段（会跑命令、可能移动文件），不产出结构化设计文档。定位类似"开工前的场地平整"。

## 输入

- 无参数：对当前项目做完整前置准备（codegraph + 文档合规 + 归位）。
- 带参数 `codegraph`：只做 codegraph 初始化。
- 带参数 `docs` / `check`：只做文档合规检查与归位方案。

## 前置检查

- 确认当前在项目根目录（有 `.git` / 明显的项目根标志）。不在则提示用户切到项目根。
- 本阶段无需探测项目画像（不涉及技术方案细节）。

## 执行

### 第一步：codegraph 初始化

检查代码检索索引是否就绪，没有则初始化——后续阶段摸代码、找引用会快很多：

```bash
# 检查是否已初始化
ls .codegraph/ 2>/dev/null && echo "codegraph 已就绪" || echo "需要初始化"

# 不存在则执行
codegraph init
```

- 已存在 `.codegraph/` → 跳过，告知"已就绪"。
- `codegraph` 命令不存在 → 不报错中断，提示用户"未装 codegraph，跳过此步；装了会加速后续代码检索"，继续走文档检查。

### 第二步：文档合规检查

对照 SDLC 文档标准（见 SKILL.md「产物目录规约」）扫描现有文档，找出不合规项。标准要点：

- 上下文资料（`00-context/`）：公司/团队架构文档、知识库、技术规范等辅助开发的参考资料，存于 `.sdlc/00-context/`。
- 研发流程产物应在项目根 `.sdlc/` 下的**数字前缀阶段目录**：`01-prd/` `02-design/` `03-review/` `04-code/` `05-test/` `06-deploy/`。
- 统计/分析报告类文档应在 `<数字>-report/` 目录下（目录名前缀是真实数字，如 `07-report/`），**目录名和文件名都必须数字前缀开头**（如 `07-report/00-xxx-report.md`）。
- **所有产物文件名以数字前缀开头，且用具体需求名而非阶段通用词**：`<数字>-<需求名>.md`（如 `00-用户登录.md`）；禁止用 `requirements`/`design`/`review` 这类阶段通用词当文件名——阶段已由所在目录区分（完整命名规约见 SKILL.md「产物目录规约」）。

扫描两个范围：

```bash
# 1) .sdlc/ 内部：目录/文件是否符合数字前缀规约
find .sdlc -maxdepth 2 -type f 2>/dev/null | sort

# 2) 散落文档：项目里游离在 .sdlc/ 之外的研发文档
#    （根目录、docs/、doc/、design/ 等常见位置的需求/设计/评审/上线/报告类 .md）
find . -maxdepth 2 -name "*.md" -not -path "./.sdlc/*" -not -path "./.git/*" -not -path "./node_modules/*" 2>/dev/null | sort
```

对每个文件判断：

- **位置合规**：是否在正确的阶段目录 / report 目录下。
- **命名合规**：文件名是否数字前缀开头。
- **归属推断**：散落文档从文件名/内容看属于哪个阶段（含"架构/知识库/规范/术语/背景资料"→ `00-context`；"需求/PRD"→ `01-prd`；"设计/方案/架构方案"→ `02-design`；"评审"→ `03-review`；"上线/发布/回滚"→ `06-deploy`；"统计/报告/分析/复盘"→ `<数字>-report`）。归属不确定的，标为"待确认"，不猜。

### 第三步：出整理方案，逐项确认后再动手

**先出方案，不要直接移动文件**（移动文件不可逆）。把不合规项整理成一张方案表给用户：

| 现路径 | 问题 | 建议动作 | 目标路径 |
| --- | --- | --- | --- |
| `docs/需求说明.md` | 位置+命名不合规 | 移动+改名 | `.sdlc/01-prd/00-需求说明.md` |
| `.sdlc/02-design/design.md` | 命名缺数字前缀、且用了阶段通用词 | 改名为需求名 | `.sdlc/02-design/00-用户登录.md` |

- 归属"待确认"的项单独列出，请用户明确它属于哪个阶段（或保持不动）。
- 用户逐项确认（可全部同意 / 部分同意 / 跳过某项）后，才用 `git mv`（在 git 仓库内，保留历史）或 `mv` 执行。移动前若目标路径已存在同名文件，停下来问，不覆盖。
- 用户未确认的项一律不动。

## 产出

- 主要是**动作**（初始化 codegraph、按确认后的方案移动/重命名文档），不强制产出文档。
- 终端输出一份**准备情况摘要**：codegraph 状态、扫描到的文档数、不合规项数、已整理项数、待确认项。
- 需要留痕时可选写 `.sdlc/00-init-report.md`（数字前缀），记录整理前后的文件映射；仅在整理动作较多、值得追溯时写。

## 交接

展示：codegraph 是否就绪 + 文档合规情况（合规/已整理/待确认）+ 一句话下一步建议。通常下一步是：

- 项目还没有需求文档 → 进入 `clarify` 从需求澄清开始。
- 已有规范的需求文档 → 可进入 `design`。
- 仍有"待确认"归属的散落文档 → 请用户先明确，再决定是否归位。

init 只做准备，不自动进入后续阶段——等用户明确指令。
