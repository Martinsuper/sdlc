# 阶段：项目/代码分析报告（report）

对当前项目**现场扫描代码库做统计与度量分析**，产出一份结构化分析报告并留档。典型主题：代码结构/模块概览、接口清单、依赖与变更影响面、复杂度/改动热点、（涉数据库时）慢 SQL 与数据量评估等。

这是**横切型、按需运行**的阶段：不属于主流程门禁链（clarify→deploy），不需要 PRD/设计/评审等前置产物，任何时刻都能跑。

与 `status` 的区别要分清：`status` 只扫 `.sdlc/` 下的**流程产物**、纯只读、结果只打在终端；`report` 扫的是**真实代码库**、做分析、**产出留档文件**到 `.sdlc/<数字>-report/`。

## 输入

- 无参数：对当前项目做一份**综合**分析报告（覆盖启用的各维度）。
- 带参数指定主题，收窄分析焦点（骨架不变，只是聚焦到该维度）：
  - `structure` —— 代码结构 / 模块与分层概览。
  - `api` / `interface` —— 对外接口清单（Controller / 路由 / 导出函数等）。
  - `deps` / `impact` —— 依赖关系与变更影响面（改某处会波及谁）。
  - `complexity` —— 复杂度、体量、改动热点。
  - 或直接给自然语言主题（如"统计最近改动最频繁的模块""梳理支付模块的调用链"）。

## 前置检查

1. 确认在项目根（有 `.git` 或明显项目根标志）。不在则提示用户切到项目根。
2. **优先用 codegraph 取数**——先看索引是否就绪：

   ```bash
   ls .codegraph/ 2>/dev/null && echo "codegraph 已就绪" || echo "codegraph 未初始化"
   ```

   - 就绪：用 codegraph 系列能力采集，又快又准——`codegraph_files`（文件树+符号数）、`codegraph_search`（找符号）、`codegraph_explore`（读某片区域源码）、`codegraph_callers`/`codegraph_callees`（调用关系）、`codegraph_impact`（变更影响面）。
   - 未就绪：提示"可先跑 `sdlc init` 建 codegraph 索引，分析会更快更准"，然后**降级**用 `find`/`grep`/Read 做静态扫描，照样产出报告。
3. **探测项目画像**：读 `references/profiles.md`，据画像决定报告**启用哪些维度**——例如探测到数据库依赖才出「慢 SQL / 数据量」维度（`[db]`），前端项目才出「组件/路由」维度，纯 CLI/库不硬塞 Web 维度。未启用的维度**直接不出现在报告里**，保持干净（复用现有裁剪机制，不重造）。探测不了就问用户一句，不硬猜。

## 执行

**第一步：确定分析范围。** 无参数→综合报告，覆盖画像启用的各维度；有参数→只聚焦该主题。

**第二步：采集数据。** codegraph 优先，降级 grep/find/Read。按主题取对应数据，例如：
- 结构：模块/包/目录划分、文件与符号数量分布、分层关系。
- 接口：Controller/路由/对外导出的清单与签名。
- 依赖/影响：关键符号的 callers/callees、`codegraph_impact` 的波及面。
- 复杂度/热点：大文件、长函数、（可选 `git log` 辅助）高频改动文件。

**第三步：结构化组织。** 按 **概览指标 → 分维度明细 → 风险与建议** 三层组织。数据要有出处（哪个模块/文件/符号），能引用 codegraph 得到的调用链或影响面就引用，让结论可追溯，不空泛。

## 产出

写一份 markdown 报告，落到 `.sdlc/<数字>-report/<数字>-<主题名>.md`。**目录名与文件名都必须以数字前缀开头**（这是 SKILL.md「产物目录规约」的硬性要求，report 目录与文件缺任一数字前缀都算不合规）。

- **目录数字取顺位**：扫描 `.sdlc/` 现有数字前缀目录取最大值 +1（如已到 `06-deploy/` 则用 `07-report/`）。report 目录可复用同一个 `<NN>-report/`——同目录下多份报告用文件数字递增（`00-结构分析.md`、`01-接口清单.md`…）。

  ```bash
  ls -d .sdlc/[0-9]*/ 2>/dev/null | sort   # 看现有数字前缀目录，定 report 目录顺位
  ```

- `<主题名>` 用**具体分析主题**的短名（如 `结构分析`、`接口清单`、`支付模块影响面`），不要用 `report` 这种通用词当文件名——阶段已由 `<NN>-report/` 目录体现。
- **文件顶部带元信息块**（对齐其它阶段产物，形成弱链条）：

  ```markdown
  ---
  项目：<项目名>
  日期：<真实当天日期>
  报告主题：<综合 / structure / api / …>
  数据来源：<codegraph 索引 / 静态扫描(grep+find)>
  关联产物：<如引用了 .sdlc/ 下某产物则列其路径，否则「无」>
  ---
  ```

  日期用执行时 `date +%F` 取真实当天日期，**不要硬编码**。

- **报告正文**用内联轻量骨架（不套死模板，主题多样时更灵活）：
  1. **概览**：项目画像 + 本次分析范围 + 关键指标（如模块数/文件数/接口数/最大影响面等，视主题而定）。
  2. **分维度��细**：按启用维度分节，每节给数据 + 出处 + 简要解读。
  3. **风险与建议**：从数据里提炼值得注意的点（如超大文件、深调用链、无测试覆盖的核心模块、慢 SQL 隐患等），给可执行建议。

写产物前确认 `.sdlc/` 及 `<NN>-report/` 目录存在（不存在则创建）。

## 交接

展示：**报告文件路径** + **一句话核心结论** + **可选下一步**（换个主题再出一份 / 针对报告里某个风险点进入 `clarify` 或 `design` 深入）。不自动跳到别的阶段——等用户明确指令。
