# 阶段：设计评审（review）

对设计文档做逐维度评审，输出结构化风险报告。评审维度按项目画像裁剪——不给独立 Web 项目挑内部基础设施的刺。

## 输入

- 设计文档路径（`.sdlc/02-design/` 下的 `00-<需求名>.md`，扫描目录定位；或用户指定的任意路径）。
- **需求文档（PRD）** `.sdlc/01-prd/` 下的 `00-<需求名>.md`——用于核对设计是否完整实现了 PRD 的全部功能（PRD 覆盖度验证）。
- 也可评审外部设计文档（internal-docs 链接 → `document-reader` 读取）。
- 也可只给数字前缀（如 `01`）快捷选中被评审的设计文档 `.sdlc/02-design/` 下 `01-*.md`（`1`/`01` 等价，PRD 取同前缀）；定位与歧义处理见 SKILL.md「产物目录规约·数字前缀选择」。

## 前置检查

1. **探测项目画像**：读 `references/profiles.md`，得出启用的评审维度标签。未启用标签对应的维度**整维跳过**，不产生评审噪音。
2. **前置门禁——必须先有设计文档**：确认 `.sdlc/02-design/` 下存在设计文档（扫描目录定位 `00-<需求名>.md`）。列出 `.sdlc/02-design/` 下的候选文件让用户选；都没有则**默认拦截**，要求先跑 design，不允许无设计空评审。
3. **读取 PRD 做覆盖度核对**：读 `.sdlc/01-prd/` 下的需求文档（`00-<需求名>.md`），抽出其「功能列表」与「验收标准」的每一条，作为 PRD 覆盖度验证（见下方执行第 0 步）的核对清单。若 PRD 缺失 → 提示：无 PRD 无法验证设计完整性，建议先补 clarify 产物（用户显式声明强制跳过时可放行，并在报告标注该验证未执行）。

## 执行

**第 0 步（强制）：PRD 覆盖度验证——设计是否完整实现了 PRD 的全部功能。**

把 PRD 的功能列表 + 验收标准逐条拉出，在设计文档里找对应的实现方案（架构/流程/接口/数据设计等哪一部分承接了它），产出一张**覆盖矩阵**：

| PRD 功能点 / 验收标准 | 设计中的对应实现 | 覆盖状态 |
| --- | --- | --- |
| （逐条列 PRD 的每个功能点） | （指向设计的具体章节/图/接口；缺失则留空） | ✅ 已覆盖 / ⚠️ 部分覆盖 / ❌ 未覆盖 |

判定规则：

- **每个 PRD 功能点都必须在设计中找到对应实现**。任何一条 `❌ 未覆盖` → 该维度记 **Block**，评审结论**不通过**（设计未完整实现 PRD）。
- `⚠️ 部分覆盖`（提到了但方案不完整、漏了异常分支/边界/非功能约束）→ 记 Warning。
- 反向也看：设计里有**PRD 未提及的功能**（超范围实现）→ 记 Warning，提示确认是否为需求蔓延或漏更 PRD。
- PRD 里标注为「范围外（Out of Scope）」的项，设计不实现是正确的，不算缺失。

覆盖矩阵作为报告的第一部分，先于逐维度评审。

**再按维度逐项核对**，每项给一个评级：

- **Pass** ✅ —— 文档已覆盖且分析合理
- **Warning** ⚠️ —— 提到了但分析不充分 / 有疑问 / 缺降级
- **Block** ❌ —— 缺失或存在明显风险，必须改

**评审维度**（带标签的维度仅在标签启用时评）：

1. **架构完整性** —— 有无架构/流程/时序图；上下游服务及负责人是否列全；同步调用超时是否考虑。图是否守绘图规范：PlantUML 且 lint 通过、图里没混大段代码、节点用中文业务名(英文类名)、单图 ≤ 8 节点、未用泳道、涉及的表/外部调用有标注、改动逻辑按语义配色（核心/一般/外部/历史不变）。
2. **数据设计** `[db]` —— SQL 是否经校验；DML 走主键索引、DQL 走索引；数据量级评估（当前+半年后）；表结构不兼容变更；找全对表/库的引用。
3. **接口设计** —— 幂等性；不兼容变更（入参/出参）；是否与上下游确认；C 端是否需缓存；主从延迟影响；找全接口引用。
4. **核心流程与降级** —— 是否影响主流程；非核心依赖有无降级；RPC 降级；涉及金额/度量单位换算是否谨慎。
5. **缓存设计** `[cache]` —— key 版本管理；大 key 风险；缓存不可用降级；新旧缓存兼容。
6. **异步消息** `[mq]` —— 消息体变更是否兼容消费方；发送/消费异常流程；重试机制。
7. **定时任务** `[job]` —— 幂等；执行失败影响；监控。
8. **监控可观测性** —— 有无监控方案；主流程/异常/关键逻辑埋点。
9. **灰度与回滚** —— 灰度策略；新旧兼容；`[frontend-compat]` 前端/客户端兼容；能否快速回滚。
10. **容量评估** —— 新增调用量是否需扩容/压测；网关/入口容量。
11. **引用完整性** —— 接口/任务/消息/配置/缓存 的引用是否找全（评审最容易发现的遗漏点）。
12. **验收标准与权衡** —— （功能点是否覆盖已由第 0 步 PRD 覆盖矩阵判定，此处不重复）验收标准是否可测量可勾选、设计给出了对应的验证方式；风险与权衡章节是否诚实（关键取舍讲清了吗，还是回避了硬问题）。

`[enterprise-infra]` 启用时才追加内部专有维度（内部网关、数仓/BI 影响等）。

## 产出

用 `templates/review-report.md` 组织，写入 `.sdlc/03-review/00-<需求名>.md`（`<需求名>` 沿用 PRD/设计的需求名，勿用 `review` 通用词）。核心内容：

- **PRD 覆盖矩阵**（第一部分）：PRD 功能点 → 设计对应实现 → 覆盖状态；列出所有 `❌ 未覆盖` / `⚠️ 部分覆盖` 项。
- **评审摘要**：总检查项 N ｜ Pass X ｜ Warning Y ｜ Block Z ｜ 结论
- **逐维度结果表**
- **风险分级**：P0（Block，必须改）/ P1（高风险 Warning，强烈建议）/ P2（中风险）/ P3（可选改进）
- **改进建议**：每条风险给具体、可执行的修改方向

**评审结论标准**：

- **PRD 有任何功能点未覆盖（❌）** → **不通过**（设计未完整实现 PRD，最高优先级红线）
- 有任何 Block → **不通过**
- 3 个以上 Warning 且关键项无降级 → **有条件通过**
- 全 Pass 或仅少量低风险 Warning → **通过**

顶部元信息块状态填评审结论。

## 交接

展示评审结论 + 风险数量分布。**评审结论是进入 code 的门禁**：

- 若**不通过 / 有条件通过** → 必须回 design 修改（我可以带着评审意见去改设计），或用户手动改，改完重新评审。**此状态下不得进入 code 阶段**。
- 若**通过** → 方可进入 code 阶段。
- 也可只看报告，稍后再处理。

用户如坚持在「不通过 / 有条件通过」状态下直接开发，需显式声明知道风险，并在评审报告状态与后续实现说明中标注「⚠️ 未通过评审即开发」留痕。
