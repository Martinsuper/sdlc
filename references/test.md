# 阶段：测试（test）

依据设计的验收标准和代码变更范围，产出测试计划并补齐测试代码，跑出真实结果。

## 输入

- 代码变更范围（git diff / 用户指定），和/或
- 设计文档（`.sdlc/02-design/` 下的 `00-<需求名>.md`）的验收标准。

## 前置检查

1. **探测项目画像**：读 `references/profiles.md`，了解测试框架惯例（pytest/junit/jest/go test/cargo test 等）。
2. **找现有测试模式**：看项目已有测试怎么写的（目录结构、命名、fixture/mock 惯例），照着来。
3. **缺代码/设计**：至少要有代码变更才能测；纯设计阶段的"测试计划"可以先写但无法执行。

## 执行

**第一步：确定测试范围与用例矩阵。** 从验收标准和 diff 推导要覆盖什么：

- **正常路径**：核心功能的主流程。
- **边界值**：空值、极值、临界条件、分页边界。
- **异常路径**：非法输入、依赖失败、超时、并发冲突。
- **兼容性**：改动是否破坏既有行为（回归）。

整理成用例矩阵：每条 = 场景 + 输入 + 预期输出 + 类型（单元/集成/e2e）。

**第二步：补齐测试代码。** 按项目既有测试风格写：

- 遵循仓库对测试的约定（如 CLAUDE.md 里"集成测试打真实数据库、不 mock"这类规则——先查有没有这类约定）。
- 测试要能真正失败——不要写永远通过的空断言。
- 不为了覆盖率凑无意义用例。

**第三步：跑测试看结果。** 用项目的测试命令实际运行，记录通过/失败/覆盖率。失败的用例要判断是测试写错了还是代码有 bug——后者要如实报告，不要改测试去迁就 bug。

## 产出

- **测试代码**（在源码树 / 测试目录里）。
- `.sdlc/05-test/00-<需求名>.md`（`<需求名>` 沿用设计的需求名，勿用 `test-plan` 通用词），用 `templates/test-plan.md` 组织：测试范围、用例矩阵、覆盖目标、**实际运行结果摘要**（通过数/失败数/覆盖率）。

顶部元信息块状态：全通过 / 有失败（附失败项）。

## 交接

展示：新增/修改的测试文件 + 运行结果（通过率、覆盖率）+ 未通过项及原因。询问用户：

- 进入 **deploy** 阶段做上线计划
- 还是先修复失败的测试/代码
- 或补充更多测试场景

有测试失败时不要跳过——先和用户确认是修复还是接受。
