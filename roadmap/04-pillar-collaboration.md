# 04. 支柱二：团队协作与企业化

> 版本：v2.0-planning（2026-07-16）
> 一句话：把 sdlc 从"个人开发者的强力 CLI"升级为"团队的协作平台" —— 异步审批、Web 控制台、可观测、自托管服务端、组织级 KB、轻量权限。
> 对应瓶颈：[01](./01-product-assessment.md) 瓶颈 2（Gate 同步阻塞）、瓶颈 4（纯单机）
> 北极星贡献：**团队协作 Pipeline 占比**（深度因子）+ **活跃团队数**（广度因子）

---

## 一、为什么这是第二支柱

北极星是"周活跃可信 Pipeline 数"。支柱一提升单个 Pipeline 的**质量**（采纳率），支柱二提升 Pipeline 的**数量与来源多样性**：

- 开源项目的长期留存，靠的是**团队采用**而非个人尝鲜。个人用完即走，团队一旦把 sdlc 织入日常研发流，就形成稳定的运行量与口碑。
- 而团队采用的**头号阻塞**正是瓶颈 2 与 4：Gate 只能同步阻塞（没人愿意让终端挂着等审批），能力只在单机（团队看不到彼此、无共享）。

**排序逻辑**：支柱二紧跟支柱一，因为它决定飞轮"有没有足够的运行样本"。但它排在 Q1 P0 加固之后 —— 主路径不通时，协作无从谈起。

---

## 二、现状 → 目标

| 能力 | 现状（代码验证） | v2.0 目标 |
|---|---|---|
| Gate 审批 | 同步阻塞，遇 block 直接 stop（`run_coordinator`） | 异步：挂起 → 通知 → 他人放行 → 自动 resume |
| 审批入口 | 仅 CLI 单进程 | CLI + Web 控制台 + IM（飞书/Slack）卡片 |
| 可观测 | CLI `trace`/`stats` 文本 | Web dashboard：Pipeline 看板 / 成本 / 质量趋势 |
| 部署形态 | 纯本地 CLI + SQLite | CLI 独立可跑 **＋** 可选自托管服务端（单二进制） |
| 多用户 | 无 | 轻量身份 + 角色（PM/TL/SRE/QA/Security）—— PRD 已设计未实现 |
| KB 共享 | 项目内 `doc/kb/` + 全局 `~/.sdlc/kb/` | 组织级 KB 服务：跨仓库、跨团队共享与订阅 |
| 通知 | Gate schema 有字段，运行时未闭环 | 通知渠道真正闭环（pending/overdue/approved/rejected） |

## 三、能力地图（4 个子方向）

```
支柱二 团队协作与企业化
├── F. 异步 Gate 与审批闭环          ← 最高优先级（解锁团队协作的钥匙）
├── G. 自托管服务端（sdlc-server）    ← 协作的承载底座
├── H. Web 控制台与可观测 dashboard
└── I. 组织 KB 共享 + 轻量权限治理
```

**架构原则（开源定位关键）**：**CLI 永远能独立跑，服务端永远是可选增强。** 不能让"必须部署服务端"成为个人用户的门槛 —— 这会吓退开源社区。服务端起步用 SQLite、单二进制、一条命令拉起。

---

## 四、子方向 F：异步 Gate 与审批闭环

### 4.1 问题本质

当前 Gate 的 schema 设计很完整（approvers / SLA / checklist / notifications），但运行时 `run_coordinator` 遇 `GateAction.BLOCK` 直接 `should_stop`、取消所有任务 —— **等于"人工把关"这个卖点在真实团队里不可用**。

### 4.2 目标流程

```
Stage 完成 → 触发 Gate（manual_review）
        ▼
Pipeline 持久化为 WAITING_APPROVAL（不占用运行进程，可关终端）
        ▼
按 Gate.notifications 推送到渠道：
  ├── Web 控制台待办
  ├── IM 卡片（飞书/Slack，带通过/拒绝按钮）
  └── 邮件（可选）
        ▼
approver 放行/拒绝/补充（带理由）→ 写回审批结果
        ▼
Pipeline 自动 resume（复用已有 resume 机制）→ 继续下一 Stage
        │
        └── SLA 超时 → 升级通知 / 按策略自动放行或阻断
```

### 4.3 关键设计决策

| 决策点 | 方案 | 理由 |
|---|---|---|
| 挂起状态存哪 | 新增 Pipeline 状态 `WAITING_APPROVAL`，存 SQLite | 复用已有状态机与 resume，不重造 |
| 无服务端时能用吗 | 能：CLI `sdlc approve <pipeline> <gate>` 本地放行 | 守住"CLI 独立可跑" |
| 有服务端时 | 服务端轮询/事件驱动，approver 在 Web/IM 操作 | 团队协作体验 |
| 审批与执行解耦 | 审批只改状态，执行由 resume 触发 | 关终端不影响待审 |
| 审批可追溯 | 审批人/时间/理由入审计（已有事件类型可扩展） | 治理与合规 |

### 4.4 与支柱一的复用

异步 Gate 的"挂起 → 通知 → 回写 → resume"机制，与支柱一子方向 C 的"结构化澄清（ask_user）"**是同一套底层机制**。合并设计，一次投入两处受益。

## 五、子方向 G：自托管服务端（sdlc-server）

### 5.1 定位

一个**可选的**轻量服务端，承载多用户协作所需的共享状态。它不改变 CLI 的核心逻辑，而是把"本地 SQLite"替换/补充为"团队共享后端"。

### 5.2 设计约束（开源友好）

| 约束 | 说明 |
|---|---|
| **单二进制 / 一条命令拉起** | `sdlc server start`，SQLite 起步，零外部依赖 |
| **CLI 无缝对接** | `sdlc config set server.url http://...`，CLI 自动把状态读写指向服务端 |
| **渐进式存储** | 默认 SQLite；团队规模大时可选 Postgres（配置切换，不强制） |
| **无供应商锁定** | 协议开放，状态可导出（已有 export/import） |
| **本地优先兜底** | 服务端不可达时，CLI 降级到本地模式，不阻塞个人工作 |

### 5.3 服务端承载的能力

- 共享 Pipeline 状态与审批队列（子方向 F 的后端）。
- 组织 KB 服务（子方向 I）。
- Web 控制台的 API（子方向 H）。
- 匿名遥测聚合（北极星度量，opt-in）。

### 5.4 关键要点

- **不做 SaaS 多租户计费**（开源定位下过早）。做"一个团队/组织自己部署一个 server"。
- 认证起步用**轻量方案**（token / 本地账号），SSO/OIDC 作为后续可选插件，不阻塞核心。
- 服务端代码开源，可自审计 —— 这是开源信任的基础。

## 六、子方向 H：Web 控制台与可观测 dashboard

### 6.1 从"文本 trace"到"可视化看板"

当前 `sdlc trace`/`stats` 是文本输出，团队无法一眼看全局。Web 控制台补齐可观测缺口（[01](./01-product-assessment.md) 雷达里 Observability 只有 3 分）。

### 6.2 控制台核心视图

| 视图 | 内容 | 服务对象 |
|---|---|---|
| **Pipeline 看板** | 所有运行中/待审/完成/失败的 Pipeline，状态流转 | 全员 |
| **审批中心** | 我待办的 Gate、SLA 倒计时、一键放行 | approver（PM/TL/SRE） |
| **Stage 详情** | 产物、reflection trace、工具调用、审计流 | 开发者、reviewer |
| **成本看板** | 按 Pipeline/团队/模型的成本，预算预警 | 平台/效能团队 |
| **质量趋势** | 采纳率、一次通过率、eval 分数随版本变化（与支柱四打通） | 平台/maintainer |
| **KB 健康度** | KB 覆盖、漂移、相关命中率 | maintainer |

### 6.3 关键要点

- 技术栈选**轻量、易自托管**（服务端内嵌静态资源，`sdlc server start` 即带 UI），不引入重前端运维。
- **只读优先**：控制台先做"看"，写操作（审批）逐步加，降低初期复杂度。
- 可观测数据来自已有的 SQLite（6 表 2 视图）+ 审计 JSONL，**数据源已具备**，主要是可视化层。

## 七、子方向 I：组织 KB 共享 + 轻量权限治理

### 7.1 组织 KB 共享

现状 KB 是"项目内 + 全局本地"。团队场景需要**跨仓库、跨团队的共享 KB**：

- 一个团队沉淀的"支付领域反模式"，其他团队能订阅复用。
- 组织级规范（安全、发布流程）集中维护，各项目继承 + 本地覆盖（复用已有 4 层加载思想）。

```
组织 KB（server）
  ├── 组织级规则/规范/架构（所有团队继承）
  ├── 领域 KB（按 bounded context 组织，可订阅）
  └── 全局模式/反模式库（跨团队抽象 —— 呼应 L3 记忆）
        │ 继承 + 本地覆盖
        ▼
项目 KB（doc/kb/，团队本地）
```

### 7.2 轻量权限治理

PRD 设计了 PM/TL/SRE/QA/Security 角色但未实现。v2.0 做**轻量、够用**的版本：

| 能力 | 范围 | 不做什么 |
|---|---|---|
| 角色 | 5 内置角色 + Gate approver 绑定 | 不做细粒度 RBAC 矩阵 |
| 审批权限 | 谁能放行哪类 Gate | 不做审批流引擎 |
| KB 写权限 | 组织级 KB 谁能改 | 不做字段级权限 |
| 审计 | 谁做了什么（已有审计扩展） | 审计上链等重治理留作可选企业模块 |

### 7.3 关键要点

- 权限做"轻量够用"，避免陷入企业 IAM 的复杂度（违反开源定位取舍原则 3）。
- 审计上链、合规报告等**重治理特性作为可选企业模块**，不进核心、不绑架社区用户。

## 九、风险

| 风险 | 缓解 |
|---|---|
| 服务端引入运维复杂度，吓退开源个人用户 | CLI 永远独立可跑；服务端单二进制 SQLite 起步；本地降级兜底 |
| Web 控制台变成重前端项目，维护成本高 | 只读优先、内嵌静态资源、不引重前端栈 |
| 权限做复杂陷入企业 IAM 泥潭 | 轻量够用，重治理作可选模块 |
| 遥测触及隐私顾虑 | 严格 opt-in、本地聚合、代码开源、匿名化 |
| IM 集成碎片化（渠道多） | 先做飞书 + Slack 两个，抽象通知接口供社区扩展 |

---

## 十、小结

支柱二把 sdlc 从个人工具变成团队平台，钥匙是**异步 Gate 闭环**（解锁协作），底座是**可选自托管服务端**，界面是**Web 可观测控制台**，纵深是**组织 KB 共享 + 轻量权限**。全程守住"CLI 独立可跑、服务端可选、本地兜底"的开源底线。它直接拉动北极星的广度（团队数）与深度（协作占比）因子。
