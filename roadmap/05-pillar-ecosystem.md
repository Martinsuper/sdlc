# 05. 支柱三：生态开放与集成

> 版本：v2.0-planning（2026-07-16）
> 一句话：让"1 个团队写的扩展，1000 个团队能用" —— 插件 SDK、模板/Adapter 市场、MCP 工具生态、A2A 协议、与 IDE/CI/IM 的原生集成。
> 对应瓶颈：[01](./01-product-assessment.md) 扩展分发缺市场（扩展点已有，发现与分发机制缺失）
> 北极星贡献：**活跃团队数 / 覆盖场景数**（广度因子）+ 社区飞轮的放大器

---

## 一、为什么这是增长引擎

sdlc 已有极好的**扩展能力**（4 层加载 + YAML 零代码扩展），但缺**扩展的分发与发现**。这就像有了插件机制却没有插件市场。

对开源项目，生态就是增长：
- **VS Code** 的护城河不是编辑器本身，是 5 万个扩展。
- **Homebrew** 的价值不是包管理器，是社区维护的数万 formula。
- **sdlc** 的长期壁垒，将是社区贡献的 Adapter（技术栈）、Profile（工作流）、Rule（规范）、Subagent（角色）、Skill（工具）的**规模**。

**它是飞轮的放大器**：支柱一四提升单点质量与可信度，支柱三把这些改进**沉淀为可复用资产并放大到全社区**。没有它，每个团队都在重复造 Adapter。

---

## 二、能力地图（4 个子方向）

```
支柱三 生态开放与集成
├── J. 插件 SDK 与贡献者工具链      ← 先让"写扩展"变简单（供给侧）
├── K. 模板 / Adapter 市场          ← 再让"找扩展、装扩展"变简单（分发侧）
├── L. MCP 工具生态 + A2A 协议       ← 让 agent 连接更广的工具与其他 agent
└── M. IDE / CI / IM 原生集成        ← 让 sdlc 嵌入研发的既有触点
```

**顺序逻辑**：先做 SDK（供给）→ 再做市场（分发）→ 工具生态与集成（连接）。没有顺滑的 SDK，市场里就没有优质内容可分发。

## 三、子方向 J：插件 SDK 与贡献者工具链

### 3.1 目标：把"写扩展"的门槛降到最低

现状写一个 Adapter 要理解 YAML schema + 内置约定，缺脚手架、缺本地测试、缺校验。贡献者体验（[02](./02-vision-strategy.md) 取舍原则 3）是开源第一优先级。

| 能力 | 现状 | 目标 |
|---|---|---|
| 脚手架 | 手写 YAML | `sdlc plugin new adapter <name>` 生成模板 |
| 本地校验 | 无 | `sdlc plugin validate` 校验 schema + 依赖 + 冲突 |
| 本地测试 | 无 | `sdlc plugin test` 用样例输入干跑，看产物 |
| 打包 | 无 | `sdlc plugin pack` 打成可分发包（含元数据/版本/签名） |
| 调试 | 靠审计日志 | `--debug` 打印 agent 决策链、注入的 context、工具调用 |

### 3.2 插件类型（覆盖全部扩展点）

```
插件（可打包分发的单元）
├── adapter   技术栈适配器（22 内置 → 社区无限）
├── profile   工作流画像（14 内置）
├── stage     自定义阶段（12 内置）
├── rule-set  规则集（548 内置规则的社区补充）
├── subagent  角色 agent（11 内置）
├── gate      审批闸门（10 内置）
└── skill     工具/技能包
```

### 3.3 关键要点

- **契约稳定**：SDK 依赖的 schema 要版本化，承诺向后兼容 —— 否则生态会因 breaking change 崩塌。
- **签名与来源**：插件包带签名与来源元数据，为市场的信任机制打基础。
- **文档即模板**：脚手架生成的模板自带注释与示例，"照着改"就能出可用扩展。

## 四、子方向 K：模板 / Adapter 市场

### 4.1 定位

一个**社区共建的扩展分发平台** —— 类比 Homebrew tap / npm registry / VS Code Marketplace。这是开源飞轮的核心引擎。

### 4.2 市场核心能力

| 能力 | 说明 |
|---|---|
| **发现** | `sdlc market search <keyword>`；Web 市场页；按技术栈/类型/热度筛选 |
| **安装** | `sdlc market install <plugin>`；自动装到 `~/.sdlc/ext/`（复用 4 层加载） |
| **发布** | `sdlc market publish`；贡献者提交（走签名 + 审核） |
| **版本** | 语义化版本；`sdlc market update`；依赖 sdlc 核心版本约束 |
| **信任** | 官方认证徽章 / 社区评分 / 下载量 / 来源可查 |
| **质量** | 提交需过 `plugin validate` + 可选 eval（与支柱四打通：市场里的 Adapter 附质量分） |

### 4.3 冷启动策略（关键）

市场最大的风险是"空市场"。策略：

1. **官方先填充**：把已有 22 Adapter + 14 Profile + 11 Subagent + 548 Rule 作为**首批官方认证内容**上架 —— 市场开张即有 50+ 优质条目。
2. **降低发布摩擦**：SDK（子方向 J）让贡献者 10 分钟能发一个扩展。
3. **激励可见性**：贡献者榜、被引用次数、"本周热门扩展"，把贡献变成社区声誉。
4. **需求引导**：公开"最想要的 Adapter"投票榜，引导社区补齐长尾技术栈。

### 4.4 关键要点

- 市场后端可复用支柱二的 `sdlc-server`，也可做成**静态 registry**（GitHub repo + index.json）起步，零运维冷启动，成熟后再服务化。
- **去中心化友好**：支持私有 registry（企业内部市场），复用 4 层加载的覆盖思想。

## 五、子方向 L：MCP 工具生态 + A2A 协议

### 5.1 MCP 工具生态

支柱一子方向 B 已把 `mcp_call` 接入 agent 工具循环。本子方向把它**生态化**：

- **MCP server 目录**：内置常用 MCP（代码检索、文档读取、API 分析等）的一键配置，社区可贡献 MCP 配置到市场。
- **能力发现**：agent 能列出可用 MCP 工具并按需调用，而非硬编码。
- **安全治理**：MCP server 白名单 + 权限分级 + 调用审计（回扣支柱一安全约束）。

### 5.2 A2A（Agent-to-Agent）协议

支柱一子方向 C 做了**进程内**的 Orchestrator-Worker。本子方向把 agent 协作**跨进程/跨系统**标准化：

```
sdlc agent  ◄──── A2A 协议 ────►  外部 agent 系统
（如 design agent）              （如某团队的专用安全审计 agent）
```

| 设计点 | 方案 |
|---|---|
| 协议基础 | 优先对齐社区标准（如 MCP 的 agent 扩展 / 开放 A2A 规范），不自造孤岛 |
| 交互契约 | 复用支柱一定义的"任务 / 结果 / 成功标准" schema |
| 边界 | A2A 是**可选高级能力**，不影响单机核心 |
| 安全 | 外部 agent 走白名单 + 能力协商 + 审计 |

**优先级说明**：A2A 是前瞻布局，放在后期季度。先把进程内多 agent（支柱一）与工具生态做扎实，A2A 水到渠成。

## 六、子方向 M：IDE / CI / IM 原生集成

让 sdlc 嵌入研发团队**已有的触点**，而非要求他们切到新工具。

### 6.1 三类集成

| 触点 | 集成形态 | 价值 |
|---|---|---|
| **CI**（GitHub Actions / GitLab CI） | `sdlc` action / job：PR 触发 review/test/security Stage，结果回帖 PR | 把 agent 织入现有 PR 流程，零习惯改变 |
| **IDE**（VS Code / JetBrains） | 轻量插件：选中代码 → 触发 Stage；查看 Pipeline 状态；审批 Gate | 开发者不离开编辑器 |
| **IM**（飞书 / Slack） | 复用支柱二通知闭环 + slash 命令触发 Pipeline | 团队协作的自然入口 |

### 6.2 关键要点

- **CI 集成优先**：对开源项目，CI 是最自然的采用入口（PR review 是刚需，且天然是团队场景 → 拉动协作占比 KPI）。
- IDE 插件做**轻量壳**（调用 CLI/server），不重造逻辑，降低多端维护成本。
- 所有集成复用已有 CLI/API 与 server，**不新增核心逻辑**，只做适配层。

## 七、里程碑与验收（季度归属见 [07](./07-roadmap-4q.md)）

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M-C1** | 插件 SDK（子方向 J） | `plugin new/validate/test/pack` 可用；文档 + 模板齐备 |
| **M-C2** | 市场 MVP（子方向 K） | `market search/install/publish`；官方 50+ 条目上架；静态 registry 起步 |
| **M-C3** | CI 集成（子方向 M 前半） | GitHub Actions 可在 PR 触发 review/test；结果回帖 |
| **M-C4** | MCP 工具生态（子方向 L 前半） | MCP server 目录 + 一键配置 + 能力发现 + 审计 |
| **M-C5** | IDE + IM 集成（子方向 M 后半） | VS Code 插件触发 Stage；飞书/Slack slash 触发 |
| **M-C6** | A2A 协议雏形（子方向 L 后半） | 跨进程 agent 协作 demo；对齐社区标准 |

### 关键 KPI

| 指标 | 基线 | 目标 |
|---|---|---|
| 市场可用 Adapter/模板数 | 0（未成市场） | ≥ 100（含社区贡献） |
| 社区贡献的扩展占比 | 0% | ≥ 40% |
| 写一个 Adapter 的耗时 | 数小时 | < 30 分钟（用 SDK） |
| CI 集成的仓库数 | 0 | ≥ 100 |
| 月活跃贡献者数 | N/A | 建立度量 + 稳定增长 |

## 八、风险

| 风险 | 缓解 |
|---|---|
| 空市场冷启动失败 | 官方先填充 50+；SDK 降摩擦；贡献激励 |
| 扩展质量参差损害口碑 | 提交过 validate + 可选 eval；官方认证徽章；社区评分 |
| schema breaking change 崩塌生态 | schema 版本化 + 向后兼容承诺 + 弃用周期 |
| 恶意/不安全插件 | 签名 + 来源可查 + 白名单 + 审计；核心权限最小化 |
| 多端集成维护成本 | 集成做轻量适配层，复用 CLI/server，不重造逻辑 |
| A2A 自造孤岛 | 对齐社区标准协议，不发明私有协议 |

---

## 九、小结

支柱三是开源飞轮的放大器：**SDK 降低供给门槛 → 市场解决分发发现 → 工具生态与集成扩大连接面**。它把支柱一四的单点改进沉淀为全社区可复用的资产，把 sdlc 的壁垒从"产品功能"升级为"生态规模"。冷启动靠官方内容填充 + SDK 降摩擦 + 贡献激励三管齐下。
