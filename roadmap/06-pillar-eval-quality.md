# 06. 支柱四：评估与质量闭环

> 版本：v2.0-planning（2026-07-16）
> 一句话：让"越用越好用"从口号变成数据 —— evals 数据集、LLM-as-judge、跨版本回归、ROI 量化、上线效果 → 决策的反馈回流。
> 对应瓶颈：[01](./01-product-assessment.md) 瓶颈 5（无评估体系），并直接解释了 §二·五 的 P0 为何会以"GA"名义漏出
> 北极星贡献：**产物采纳率的可信度**（度量与保障）+ 反哺支柱一的改进信号

---

## 一、为什么这是"隐形的地基"

前三个支柱都在"造能力"，支柱四在"证明能力真的有用、且没变差"。它回答三个致命问题：

1. **换模型/改 prompt，产物是变好还是变差？** —— 没有 eval 就是盲改。
2. **v2.0 比 v1.0 强在哪，有数据吗？** —— 没有回归就只能靠感觉。
3. **凭什么让团队信任并采纳 agent 产物？** —— 没有质量分就是空口白话。

**它还有一个特殊使命**：[01 §二·五](./01-product-assessment.md) 的 P0（端到端主路径断裂却以 GA 发布）之所以发生，正是因为**缺少"真实补全的端到端评估门禁"**——单测全绿掩盖了主路径全红。所以支柱四不是锦上添花，是**防止"绿色单测掩盖红色主路径"的必需品**，且必须提前。

**它是飞轮的信号源**：支柱一的 agent 改进、支柱三市场里的扩展质量，都需要支柱四来量化"到底好不好"，才能形成"改进 → 度量 → 再改进"的闭环。

## 二、现状 → 目标

| 能力 | 现状 | v2.0 目标 |
|---|---|---|
| 测试 | 965 单元/集成/E2E 测试（验证"代码正确"） | **＋** agent 产物质量评估（验证"产物好用"） |
| 端到端门禁 | 无真实补全冒烟（P0 因此漏出） | release 前全 Profile 真实补全冒烟必绿 |
| 产物质量度量 | 无 | eval 数据集 + LLM-as-judge 打分 |
| 版本对比 | 无 | 跨版本回归：新版 vs 旧版产物质量 diff |
| ROI | CostTracker 记成本，无收益侧 | 省时/降缺陷/加速发布的量化 |
| 反馈回流 | 反模式计数 | 上线效果 → 决策效果分 → agent 消费 |

## 四、子方向 N：端到端冒烟门禁（最高优先级）

### 4.1 问题直击

GA 发布了主路径 100% 失败的版本，根因是**没有一个"真实调用 LLM 跑完一个 Pipeline"的发布门禁**。`sdlc llm test` 只查 provider 初始化，`doctor` 不探活 —— 都是"假绿"。

### 4.2 目标：真实补全的冒烟门禁

| 门禁 | 内容 | 触发时机 |
|---|---|---|
| **烟囱测试** | 用真实（或本地 Ollama）模型，对每个 Profile 跑一个最小 Pipeline 到完成 | 每次 release 前，CI 必过 |
| **doctor 探活升级** | 检查 LLM key + 发一次真实最小补全 + 校验 temperature 等参数兼容 | `sdlc doctor` 每次运行 |
| **llm test 升级** | 发真实补全请求（非仅初始化），暴露运行时参数错误 | 用户配置后 |
| **错误可见性门禁** | 断言失败时 stage error 冒泡到终端（防错误吞没回归） | CI |

### 4.3 关键要点

- **用本地 Ollama 做 CI 冒烟**：零成本、可复现、不依赖付费 key —— 完美契合开源定位。
- 这是 Q1 P0 加固的**验证手段**：修完 temperature/错误吞没后，冒烟门禁保证它们不再回归。
- 门禁本身开源可复现，社区贡献者提 PR 时能自己跑。

## 五、子方向 O：Agent 产物 Eval 体系

### 5.1 三层评估金字塔

```
        ┌────────────────────────────┐
        │  L3 端到端 Pipeline eval     │  少量、真实场景、贵
        │  （整条流水线产物质量）        │
        ├────────────────────────────┤
        │  L2 Stage-level eval         │  中量、每个 Stage 产物打分
        │  （design/impl/cr 产物质量）   │  LLM-as-judge 为主
        ├────────────────────────────┤
        │  L1 单元 eval                │  大量、快、便宜
        │  （工具调用/解析/路由正确性）   │  规则/断言为主
        └────────────────────────────┘
```

### 5.2 Eval 数据集

| 数据集 | 内容 | 来源 |
|---|---|---|
| **黄金集** | 精选的"输入 → 理想产物"对，人工标注 | maintainer 维护，开源可复现 |
| **回归集** | 历史真实 Pipeline 的输入 + 当时产物 | 从审计日志/Artifact 沉淀（opt-in 脱敏） |
| **对抗集** | 已知会出错的 case（如 P0 触发场景、边界需求） | 从事故/bug 沉淀 |

### 5.3 LLM-as-judge

- 用更强模型（可配 `judge_model`）对 Stage 产物按维度打分：**正确性 / 完整性 / 是否遵守 Rule / 是否贴合 KB 上下文**。
- **与支柱一复用**：Plan-Act-Reflect 的 reflect 判据、judge 的评分维度，是同一套 acceptance_criteria + Rule 库，一次定义多处用。
- **judge 自身要校准**：judge 的打分定期与人工标注对齐，防止"裁判也不准"。

### 5.4 跨版本回归

```
新版 sdlc / 新 prompt / 新模型
        ▼
在黄金集 + 回归集上跑 eval
        ▼
对比基线版本的分数
        ▼
┌─────────────┬──────────────┐
│ 分数↑或持平  │ 分数↓（回归）  │
│ → 可发布     │ → 阻断 + 定位  │
└─────────────┴──────────────┘
```

这是支柱一"agent 改进"和支柱三"市场扩展质量"的**质量守门员**：任何改动都要证明"没让产物变差"。

## 六、子方向 P：ROI 量化

### 6.1 从"记成本"到"算收益"

现有 CostTracker 只记 LLM 成本（且因网关无 pricing，cost 常为 0 —— 需一并修）。ROI 要补收益侧。

| 维度 | 度量 | 数据来源 |
|---|---|---|
| **省时** | agent 完成 vs 人工基线的时间差 | Stage 耗时 + 人工基线（团队标定） |
| **降缺陷** | 用 sdlc 的 CR/test Stage 后，逃逸缺陷变化 | 与线上缺陷数关联 |
| **加速发布** | 需求上线周期变化 | Pipeline 时间线 + 部署记录 |
| **成本** | LLM 成本 + 人工审批时间 | CostTracker（修复 pricing）+ Gate 耗时 |

### 6.2 关键要点

- ROI 报告进 Web 控制台质量趋势视图（支柱二）。
- 开源定位下，ROI 数据**可脱敏共享**，让社区能对比"sdlc 到底省了多少" —— 成为口碑与采用的依据。
- 先修 CostTracker 的 pricing 缺失（网关无 pricing → cost 恒 0，`stats` 失真），否则 ROI 的成本侧是错的。

## 七、子方向 Q：反馈回流学习（与支柱一共建）

评估体系产出的信号，最终要**回流成 agent 的改进**，闭合飞轮。此处讲评估侧如何**产出**信号；agent 侧如何**消费**见 [03 子方向 E](./03-pillar-agent-intelligence.md)。

```
     eval 分数 + 上线效果 + 人类采纳信号
              ▼
      归因：哪个 decision/pattern/agent/prompt 导致的
              ▼
    ┌────────────────────────────────┐
    │ 效果分写回 KB（ADR.outcome / 模式分）│
    │ prompt/模型选择的 A/B 结果沉淀       │
    └────────────────────────────────┘
              ▼
   支柱一消费：高分决策优先注入，低分反模式规避
              ▼
   下一轮 eval 验证是否真的变好 ──（闭环）
```

### 关键要点

- **闭环必须有验证**：反馈学习后，必须用回归集验证"确实变好而非强化了偏好"。这是防止 agent 自我固化错误的安全阀。
- 归因要**足够样本才生效**：单次信号不改行为，避免噪声驱动。

## 八、里程碑与验收（季度归属见 [07](./07-roadmap-4q.md)）

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M-D1** | 端到端冒烟门禁（子方向 N） | 全 Profile 真实补全冒烟 CI 必过；doctor/llm test 真实探活；P0 不可回归 |
| **M-D2** | Eval 框架 + 黄金集（子方向 O 前半） | eval 可跑；黄金集 ≥ 每 Stage 10 例；LLM-as-judge 打分 |
| **M-D3** | 跨版本回归（子方向 O 后半） | 每次 release 附回归报告；分数下降阻断发布 |
| **M-D4** | ROI 量化（子方向 P） | CostTracker pricing 修复；省时/降缺陷/加速发布可报告 |
| **M-D5** | 反馈回流学习（子方向 Q） | eval + 上线效果 → 效果分 → agent 消费；回归验证不退化 |

### 关键 KPI

| 指标 | 基线 | 目标 |
|---|---|---|
| 覆盖 eval 的 Stage 占比 | 0% | 100% |
| 每次 release 附回归报告 | 0% | 100% |
| 端到端冒烟通过率 | 0%（P0） | 100% |
| judge 与人工标注一致率 | N/A | ≥ 85% |
| ROI 可量化的团队数 | 0 | ≥ 20 |

## 九、风险

| 风险 | 缓解 |
|---|---|
| LLM-as-judge 本身不准 | 定期与人工标注校准；一致率进 KPI |
| eval 成本高（每次跑烧钱） | 分层金字塔（L1 便宜量大，L3 少而精）；CI 用 Ollama |
| 回归集含敏感数据 | opt-in + 脱敏；黄金集用合成/公开数据 |
| 反馈学习强化错误偏好 | 回归集验证 + 足够样本门槛（与支柱一共守） |
| ROI 人工基线难标定 | 团队自标 + 提供默认基线模板；先做相对趋势不追绝对值 |

---

## 十、小结

支柱四是"隐形的地基"：**端到端冒烟门禁**堵住 P0 漏出（GA 的教训），**eval 体系 + 回归**让每次改动可度量、不退化，**ROI 量化**向社区证明价值，**反馈回流**把评估信号变成 agent 改进、闭合飞轮。它让"越用越好用"第一次有了数据支撑，也是支柱一三的质量守门员。**因其防漏出的使命，它的子方向 N 必须与 Q1 P0 加固同步启动。**
