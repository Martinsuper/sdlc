# 阶段：需求澄清（clarify）

把一个模糊的需求变成结构化、可验收的功能规格，为后续设计打地基。这是全流程的起点，也常常是省不掉的一步——设计和评审的质量上限由这里决定。

## 输入

- 用户的自然语言需求描述，或
- PRD 链接（internal-docs `internal-doc.example` / internal-docs `internal-doc.example` → 用 `document-reader` MCP 读取），或
- 一段零散的想法。

## 前置检查

- 若给了 PRD 链接，先读全文再澄清，不要只凭标题猜。
- 若需求已经很清晰且用户明确说"不用澄清，直接设计" → 跳到 design 阶段，不必强行走完本阶段。
- 本阶段无需探测项目画像（还没进入技术细节）。

## 执行

分两轮，别一次抛太多问题淹没用户：

**第一轮：识别模糊点，生成澄清清单。** 通读需求，从这些角度找出"没说清楚 / 有多种理解 / 有隐含假设"的点：

- **范围边界**：做什么、明确不做什么；这次和下次的分界。
- **功能细节**：核心流程的每一步输入/输出/异常分支；边界值。
- **数据**：涉及哪些实体、来源、量级、生命周期。
- **非功能约束**：性能（QPS/延迟）、并发、一致性要求、安全/权限、合规。
- **兼容性**：是否改动既有接口/数据结构；对存量用户/数据的影响。
- **依赖与协作**：依赖哪些上下游、谁提供、是否已对齐。
- **验收标准**：怎样算"做完了"、怎样算"做对了"。

把这些整理成**编号问题清单**给用户，一次问 5–10 个高价值问题，标出哪些是阻塞性的（不回答无法设计）。

**第二轮：固化规格。** 用户回答后（可能多轮），把澄清结果整理成结构化功能规格：

- 需求背景与目标（一句话价值 + 要解决的问题）
- 功能列表（每条：描述 + 输入 + 输出 + 主要流程 + 异常处理）
- 非功能需求（性能/安全/兼容性/合规，逐条量化）
- 明确的范围外事项（Out of Scope）
- 验收标准（可测量、可勾选）
- 尚未解决/待外部确认的开放问题

## 产出

写入 `.sdlc/00-clarify/00-requirements.md`。顶部元信息块：

```
> 需求名称：<name>
> 日期：<YYYY-MM-DD>
> 状态：已澄清 / 待确认（有开放问题）
> 关联：（暂无）
```

## 交接

展示产出路径 + 需求一句话摘要 + 开放问题数量。询问用户：

- 进入 **design** 阶段（我会带着这份规格做方案设计）
- 还是先补充/修改澄清内容
- 或有开放问题需要用户去外部对齐后再继续

若用户选择继续，进入 `references/design.md`，并把本产出作为 design 的主要输入。
