# 阶段：编码实现（code）

把设计变成代码。这一步 Claude Code 本体最擅长——本阶段的职责是**编排 + 规范注入 + 自检**，而不是复述如何写代码。

## 输入

- 设计文档路径（`.sdlc/01-design/00-design.md`），或
- 用户直接指定的开发单元/改动点。

## 前置检查

1. **探测项目画像**：读 `references/profiles.md`，了解技术栈——影响遵循的编码规范（命名、分层、错误处理惯例）。
2. **读现有代码规范**：若项目有 `CLAUDE.md`、`.editorconfig`、lint 配置、或明显的代码风格，遵循它们，不要引入与现有风格冲突的写法。
3. **缺设计文档**：简单改动可直接做；复杂需求建议先有设计，否则容易返工。

## 执行

**第一步：拆解开发单元。** 从设计文档拆出有序的开发单元（按依赖关系排序：数据结构/模型 → 数据访问 → 业务逻辑 → 接口层 → 前端对接）。单元之间有依赖时串行，独立时可并行。

**第二步：逐单元实现。** 每个单元：

- 遵循项目既有模式（找一个类似的现有文件参照），不要另起一套。
- 只做设计要求的改动——不顺手重构、不加设计外的抽象、不加用不到的错误处理（遵循仓库 CLAUDE.md 的工程约束）。
- 涉及外部边界（用户输入、外部 API）才做校验；内部调用信任类型与框架保证。

**第三步：自检。** 每个单元或一组相关单元完成后，建议调用现成能力自检，别自己重造：

- `code-review` skill —— 审当前 diff 的正确性与可简化点。
- `verify` skill / `run` skill —— 端到端跑一遍受影响的流程，确认真的能用（尤其 UI/接口改动，类型检查通过 ≠ 功能正确）。
- 项目已有的 lint / type-check / 测试命令。

## 产出

- **主产出是代码变更本身**（在源码树里）。
- 可选：`.sdlc/03-code/00-impl-notes.md` 记录实现说明——只在有"设计外的决策/权衡/坑"值得留痕时写，否则不写（避免为凑文档而写文档）。若写，包含：实现与设计的偏差及原因、遗留 TODO、需要评审注意的点。

## 交接

展示：改了哪些文件（概要）+ 自检结果（lint/测试/verify 是否通过）+ 与设计的偏差（若有）。询问用户：

- 进入 **test** 阶段补齐测试
- 还是继续实现下一批单元
- 或做一次完整的 code-review

如果自检发现问题且无法当场解决，如实说明，不要谎报"已完成"。
