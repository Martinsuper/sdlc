# 阶段：设计评审（review）

对设计文档做逐维度评审，输出结构化风险报告。评审维度按项目画像裁剪——不给独立 Web 项目挑内部基础设施的刺。

## 输入

- 设计文档路径（`.sdlc/01-design/00-design.md`，或用户指定的任意路径）。
- 也可评审外部设计文档（internal-docs 链接 → `document-reader` 读取）。

## 前置检查

1. **探测项目画像**：读 `references/profiles.md`，得出启用的评审维度标签。未启用标签对应的维度**整维跳过**，不产生评审噪音。
2. **缺设计文档**：列出 `.sdlc/01-design/` 下的候选文件让用户选；都没有则建议先跑 design。

## 执行

按维度逐项核对，每项给一个评级：

- **Pass** ✅ —— 文档已覆盖且分析合理
- **Warning** ⚠️ —— 提到了但分析不充分 / 有疑问 / 缺降级
- **Block** ❌ —— 缺失或存在明显风险，必须改

**评审维度**（带标签的维度仅在标签启用时评）：

1. **架构完整性** —— 有无架构/流程/时序图；上下游服务及负责人是否列全；同步调用超时是否考虑。
2. **数据设计** `[db]` —— SQL 是否经校验；DML 走主键索引、DQL 走索引；数据量级评估（当前+半年后）；表结构不兼容变更；找全对表/库的引用。
3. **接口设计** —— 幂等性；不兼容变更（入参/出参）；是否与上下游确认；C 端是否需缓存；主从延迟影响；找全接口引用。
4. **核心流程与降级** —— 是否影响主流程；非核心依赖有无降级；RPC 降级；涉及金额/度量单位换算是否谨慎。
5. **缓存设计** `[cache]` —— key 版本管理；大 key 风险；缓存不可用降级；新旧缓存兼容。
6. **异步消息** `[mq]` —— 消息体变更是否兼容消费方；发送/消费异常流程；重试机制。
7. **定时任务** `[job]` —— 幂等；执行失败影响；监控。
8. **监控可观测性** —— 有无监控方案；主流程/异常/关键逻辑埋点。
9. **灰度与回滚** —— 灰度策略；新旧兼容；`[frontend-compat]` 前端/客户端兼容；能否快速回滚。
10. **容量评估** —— 新增调用量是否需扩容/压测；网关/入口容量。
11. **引用完整性** —— 接口/任务/消息/配置/缓存 的引用是否找全（评审最容易发现的遗漏点）。
12. **需求覆盖与权衡** —— 验收标准回链是否逐条对上、有无"未覆盖"缺口；风险与权衡章节是否诚实（关键取舍讲清了吗，还是回避了硬问题）。

`[enterprise-infra]` 启用时才追加内部专有维度（内部网关、数仓/BI 影响等）。

## 产出

用 `templates/review-report.md` 组织，写入 `.sdlc/02-review/00-review.md`。核心内容：

- **评审摘要**：总检查项 N ｜ Pass X ｜ Warning Y ｜ Block Z ｜ 结论
- **逐维度结果表**
- **风险分级**：P0（Block，必须改）/ P1（高风险 Warning，强烈建议）/ P2（中风险）/ P3（可选改进）
- **改进建议**：每条风险给具体、可执行的修改方向

**评审结论标准**：

- 有任何 Block → **不通过**
- 3 个以上 Warning 且关键项无降级 → **有条件通过**
- 全 Pass 或仅少量低风险 Warning → **通过**

顶部元信息块状态填评审结论。

## 交接

展示评审结论 + 风险数量分布。询问用户：

- 若不通过/有条件通过 → 回 design 修改（我可以带着评审意见去改设计），或用户手动改
- 若通过 → 进入 code 阶段
- 也可只看报告，稍后再处理
